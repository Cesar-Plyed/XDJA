# September 30, 2026

First entry — Admin dashboard: reviews moderation + session refresh work.

- **Delete confirmations use an in-theme `role="alertdialog"` modal** (not `window.confirm`): native dialogs can't be themed or translated, and the guidelines require confirmation before destructive actions. Escape/backdrop/Cancel all cancel; focus moves into the dialog on open.
- **Overview "Pending reviews" stat → "Recently deleted"**: the backend has no pending concept, but it does keep `GET /api/reviews/history` for 30 days, so the stat now shows real data (`total_reviews` also wired to the real count; the old hardcoded `0`s were placeholders).
- **Tab state lives in the URL (`/admin?tab=reviews`)** via `useSearchParams` so dashboard sections are deep-linkable and survive reload/back. Pagination page numbers stayed in component state — deep-linking them was explicitly cut from scope during planning.
- **Silent refresh is single-flight in `src/lib/api.ts`**: refresh tokens are single-use and rotated, so two concurrent refreshes with the same token would mean one always gets 401 → forced logout. Every 401 therefore shares one in-flight `POST /auth/refresh`, then retries once. Outcome policy: 200 → rotate+retry; 401 → clear both tokens (UI redirects to /login); 503/429/network → keep tokens and show a retryable error (backend explicitly says these are transient, so logging out would be wrong).
- **`getProjects`/`getReviews` send the bearer header when a token exists and are wrapped in the same refresh logic** even though the real backend treats them as public — uniform 401 recovery, and it made the endpoints safe to require auth later. Public routes ignore the extra header.
- **`useReviewHistory` skips its fetch when no session exists** — visiting `/admin` unauthenticated used to fire a doomed 401 before the redirect; now it resolves quietly.
- **Local backend runs with `npm run dev:api`, not `npm run dev`** (the latter is the Vercel serverless entry that just exports the app and never listens). Local `.env` has *empty* Upstash vars, so locally login omits `refreshToken` and refresh answers 503 — that degraded mode is expected, not a bug; refresh flows were verified against a scripted mock (scenarios: rotate-ok / 401 / 503).
- **`handleDeleteProject` previously never called the API** (it only logged to console) — it now opens the shared confirm dialog and awaits `api.deleteProject`, refetching projects/reviews/history afterwards (project delete moves its reviews to history).
- **Guidelines pass** removed every `transition: all` (explicit props), added `:focus-visible` rings, `prefers-reduced-motion`, `overscroll-behavior: contain` on modal overlays, `color-scheme` per theme, `tabular-nums` on stats/table, `…` instead of `...` in translations, and a default `aria-hidden="true"` on `Icon`.
- **Destructive delete was tested on the real stack with zero residue** (user-approved): inserted a temp review via `prisma db execute`, deleted it through the real UI (`DELETE` → 200, list/history/stats all updated, the one real customer review untouched), then scrubbed its `review_history` row — final state: 1 public review, 0 history rows. The real customer review itself was never deleted (there is no restore endpoint, only the 30-day history).
- **Production CORS fix (backend repo, same day):** the dashboard's cross-origin `DELETE`s were rejected by the backend preflight (`Allow-Methods: GET,POST` only) — fixed in `xdja-backend` (`fix: allow DELETE in CORS preflight`, `security.ts`), not here. Local dev never hit it because the Vite proxy makes `/api` same-origin, so preflights only run cross-origin in production. Both `API_DOCS.md` CORS sections now document the allowed methods/headers and the 86400 s preflight cache (browsers may keep refusing DELETE for up to 24 h after the deploy — an incognito window confirms the fix).
